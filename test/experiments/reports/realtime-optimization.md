# 流式时间戳优化与严格验收

日期：2026-11-15。服务器，无录音播放设备、无机器人、无录音上传。

结论：**仍未全部达标，保留综合最佳的尽力同步方案。** 17 组配置在三个样本上共 51 次墙钟回放，最佳为 314/327（96.0%）同时满足一字容差与提前发布；没有放宽验收来宣布成功。`GuideBot/gesture/timing.py` 保存该配置，`--gestures` 使用它，单独 `--timestamps` 默认不改。

## 验收协议

参考值为原始 FP32 FunASR 在完整音频与完整文本上执行的最终强制对齐，不是人工标注。三个参考文件固定后，各方案均与同一参考比较；没有用参考时间戳安排实时输出。原生 Qwen 离线结果另有历史对照，包含零时长区间，不能不经处理就作为“一字完整时长”的分母。

每个文字单元记录：参考起点 `s`、终点 `e`、首次输出起点 `p`、首次发布对应播放位置 `r`。

- 误差通过：`abs(p-s) <= e-s`；缺失计失败。
- 实时通过：`r <= s`；不因预测起点偏晚而放宽期限。
- 联合通过：上述两项同时成立。
- 另统计截止参考起点前的最新修订，不能把事后修复冒充实时通过。

中文逐字；沿用系统既有规则，英文词与数字串各为一个单元。因此混合文本样本单独列出。三个完整回复分别为 26、104、197 单元，音频 6.82、22.68、45.48 秒，总计 327 单元。参考区间最短约 80ms，中位 180–200ms，容差不是固定的一秒或固定的平均字长。

所有回放沿用日志真实音频包到达时刻、完整文本到达时刻与预计播放起点。旧日志没有 transcript delta 的正文，不能重建真实增量文本；没有提前把全文送给模型。`client.cloud-done` 不等于播放结束。对齐模型在回放前加载，启动耗时不混入单字延迟；没有增加语音缓冲。

`optimize_realtime.py` 使用同一模型、单个推理循环，在每轮结束后消费所有已到达输入，按 latest-wins 处理。这是测得实际计算耗时的墙钟回放，不是加速虚拟时间；它不含独立进程 IPC 和动作服务开销，所以最终候选还需用真实 `StreamingTimestamps` 子进程验证。各轮共享服务器负载未固定，不能把不同回放的差异全部归因于一个参数。

“前两秒以外”仅为诊断分层，不是替用户规定的豁免范围；严格总分始终保留开头失败。用户允许牺牲开头动作，但这不能掩盖中段错误。

## 已确认的原因

1. **队列已经合并最新输入。** 回归探针在一次 1s 音频推理中追加三个 0.5s 包，下次实际输入为 2.5s，没有依次计算 1.5/2.0/2.5s。`coalesced_step_thresholds` 表示合并跨过的步长阈值，不是丢弃过的真实推理任务。
2. **局部游标误差会累积。** 缩窗改善耗时却可能导致计数偏移、顺序冲突和 cursor_lost。完整前缀固定从 index=0 开始，明显减少累积漂移。
3. **特征缓存不是首要收益点。** `gesture-profile-baseline` 的 15 次实际推理包括两个被拒绝窗口：总计算 16.89s，frontend 4.01%、encoder 62.21%、两次 predictor 合计 33.56%。不能把这次分解倒推成历史某一轮 2.143s 的精确分解。
4. **增加线程未必加速。** 单/双/四线程都实际测量；本机单线程通常更好。系统负载曾约 80，40 个逻辑核；负载也含 NFS I/O 等待，不能仅据 load average 断言纯 CPU 争抢。模型初始化曾主要等待远端文件系统，回放入口允许最多 300s 预加载，在线原有 60s 默认未改。
5. **音频与文本余量需分开。** 本批录音中，所有字的完整音频都曾在其参考起点前到达；但长回复开头两个字的完整文本到达晚于参考起点。零计算成本也不能从这些旧日志忠实重建那两个字的及时文本锚点。中段仍有误差和迟到，不能一律归因于音频到得慢。
6. **模型不是文本音素匹配器。** 当前 predictor 主要根据声学边界与文字数量分配时间；未知完整前缀的字数估计、停顿附近的峰选择、混合英文的单元定义都会影响位置。完整前缀仍可能来回修订，更多上下文不保证单调改善。

## 保留方案的量化边界

保留 `threads=1, quantized=True, reuse_predictor=True, count_offset=-1`，对齐参数为 `window=120, step=.5, tail=.1, resync_every=0, final_repair=True`。不需要 ONNX 执行器。完成时使用真实已到达的全文长度修复，没有提前获知未来音频。

- 全部：覆盖 327/327，准确 316/327，提前发布 324/327，联合通过 314/327。
- 首次绝对误差：中位 40ms、P95 194ms、最大 540ms。P95 低于平均字长不代表每个字通过。
- 104 单元中文：103/104 联合通过，全部提前发布，最小首次发布余量约 71ms；“厅”误差 360ms，容差 240ms。
- 197 单元中文：193/197 联合通过，3 个开头单元迟到；“区”误差 520ms，容差 240ms。
- 两段纯中文合计：296/301 联合通过。前两秒以外 281/283 联合通过，两个中段误差仍失败。
- 混合英文短句：18/26 联合通过，最大误差 540ms。GuideBot 按一个词单元处理，声学计数没有显式发音词典；不能承诺混合文本通过。
- 最差首次发布落后参考起点约 567ms，出现在长回复开头；首发余量中位约 2.61s。

上述是三个样本的测量结果，不是新录音上的准确率保证。服务器没有固定推理资源，完整前缀成本随长度增加，120 秒只是输入上限，不是已经验证的实时能力上限。当前最长验证 45.48s。旧日志缺增量文本正文，也没有真实 DAC 反馈，不能把这些结果当成现场全链路通过。

## 整体设计建议

继续保持语音不等待。LLM 输出语义上的切换/到位 unit_id，时间戳负责把它们映射到可修订的播放位置；LLM 不猜秒数。已有调度器在提交前接受修订，提交后冻结，到位期限已过则跳过，开始晚而到位未过则压缩切换。底层能严格按要求到位，也不能修复上层文字锚点本身的时间误差。

稀疏动作可以使用该保留方案尽力同步，但不能向执行器承诺所有锚点都准确或提前。应分别保留计划就绪、锚点首发、修订、命令提交、预测到位和参考偏差，不用单一“处理音频耗时”掩盖结果质量。

若必须对新输入继续追求严格边界，优先改变可用信息：让语音生成端同时给出词/音素标记或内部时长，语音本身不必等待外部对齐。历史已核对的 ASAPRealizer `WordIU/TimePeg` 正是利用合成器内部时序，Greta 也提供增量行为规划参考，详见 `action-anchor-improvement.md`。如果语音接口始终只有黑盒音频，则需要内容条件的因果对齐器及明确的右上下文、提交和修订协议；现有全注意力 SANM 与双向 LSTM 的编码状态不能直接当成流式缓存。GPU 或 ONNX 可降低计算耗时，但不会自动消除“区”这个定位歧义。相关替代项目和 Qwen CPU 失败证据见既有候选调研与对照报告，未将它们冒称为本轮已通过的新方案。

## 试听的因果约束

`realtime-markers.wav` 保留原音频总时长，叠加 30ms 提示音。播放前收到的修订会更新尚未响的提示；已经响过的提示不回跳。若边界发布时预测位置已过，提示在真实发布时间才响。多个迟到提示可能重叠，详见 markers.json；超出回复结束的提示不延长语音。`reference-markers.wav` 仅为离线理想边界对照，不能作为实时效果展示。

动作试听通过 `render_gesture_realtime.py` 从实际后台进程生成的 `gesture.command` 制作：低音表示切换开始，高音表示预计到位，低沉长音表示跳过。参考版用离线时间作同样标记。它们不是机器人实际动作或 DAC 实测，底层按时到位是用户给定的接口假设。
