**本轮DeepSeek API比本地Qwen最佳非思考方案更准确，也更快。优势主要来自动作判断，而不是引用格式。**

API配置请求名为`deepseek-chat`，112次响应的`model`字段均为`deepseek-flash`。结果对应这次实际返回的服务，不应当作旧版DeepSeek某个固定权重版本的结论。

## 差别主要在哪里

Qwen对“不要看左边的展柜”“中央控制室昨天完成维护”等文本仍会安排展示动作，也会对部分接待/空记录正例返回空动作。DeepSeek在这些对应样本上更能遵守定义。

96条里两者共同通过81条；DeepSeek单独通过13条；Qwen单独通过1条；共同失败1条。按当前family字段聚类的配对bootstrap差值区间为7.3至18.8个百分点，仅描述当前开发材料的波动。

DeepSeek的两个主指标失败值得保留：

1. “我先为大家介绍一下，请看中央的立体城市模型。”它除了中央展示，还额外安排接待动作。Qwen在这条正确。
2. “刚才环境嘈杂，我没有听清您的问题。”字典要求明确请求听众重说；两者都推断出了重听动作，属于超出原文明示条件。

因此DeepSeek也会过度推断；引用完全合法仍可能选错动作。详见[全部成对差异](paired-failures.md)。

## JSON约束没有解释这次差距

保持同一full提示，将Qwen从JSON Schema改为JSON object，与DeepSeek使用相同输出模式，再跑同96条：仍是**82/96、正例召回93.8%、负例误触发11/48**，非空请求中位1.52秒。

这排除了“只有Qwen被Schema限制、因此才表现差”的简单解释。两家不同tokenizer、推理后端和云端默认策略并未全部统一，本轮比较的是这两种实际接口配置，不能拆解成单一架构原因。

## 16条挑战单列

DeepSeek通过14/16。两个失败没有混进96条明确主指标：

- “欢迎。”没有可用的前后引用，却仍安排动作并把begin和finish设成同一起点。
- 四意图挑战返回4个动作，违反最多3个的契约；欢迎动作的两个引用也同起点。额外“按出现顺序保留前三个”仅为该挑战的规则。

因此即使采用DeepSeek，现有动作数量和原文绑定校验仍有实际用途。本轮没有放宽这些检查。

## 部署取舍与适用边界

| 方面 | 本地Qwen3-1.7B | DeepSeek API |
| --- | --- | --- |
| 联网 | 推理可离线 | 依赖API连接 |
| 机器人资源 | 占本机GPU和内存 | 模型推理在服务端 |
| 费用方式 | 无逐次API账单，消耗本机算力 | 按服务计费，本轮不估算单价 |
| 本轮实测 | 动作判断错误较多，活动输出约1.52秒 | 判断更好，活动输出约0.77秒 |

若优先考虑当前动作语义质量与响应速度，DeepSeek是本轮更合适的方向。若需要离线运行，则本地Qwen仍有部署价值，但现有1.7B方案的误触发/漏选需要继续解决。

这次使用的是虚构动作与共同的Qwen优化提示，尚未证明仅切换生产provider就能复现97.9%。需要映射回真实动作表后做生产文本和时序验收；本轮没有更改线上provider、提示或协议。

样本由同一助手合成复核，全部已属于开发材料，不是独立盲测。DeepSeek单遍，云端别名可能随服务更新，时延是本时段实测而非SLA。测试使用串行请求和复用HTTP连接，Qwen在服务ready后计时，启动时间不计入；API固定前缀多为缓存命中。未测音频交互或轨迹执行。
