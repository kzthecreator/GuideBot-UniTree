已接入真实会话入口，通过 `--timestamps` 启用。使用历史会话按实际音频到达节奏验证了后台进程；机器人现场与 AEC 并行运行仍需手动验收。

## A 处理流程

扬声器最终收到的 16 kHz PCM 同时送入独立进程。音频播放不等待对齐计算。

近期窗口约 6 秒，每增加约 2 秒音频更新一次，暂留最后 1 秒。约每 10 秒进行前缀重同步；完整回复结束后进行全段修复。积压时合并请求，只计算最新状态。

中断时取消对应回复，丢弃晚到结果。模块失败时语音继续运行。

这是离线 MonotonicAligner 的窗口化增量处理，不是模型原生流式推理。模型主要利用文本长度预测边界，不能验证音频是否真的说出了对应文字。

## B 实际进程回放结果

样本包含 45.48 秒音频、197 个字级单元。按原会话音频包到达时刻回放，无机器人录放音或云端调用。

| 指标 | 结果 |
|---|---|
| 临时更新 | 19 次 |
| 最终覆盖 | 197 / 197 |
| 近期窗口计算 | 中位 0.730 秒，最大 1.060 秒 |
| 前缀重同步 | 4 次，中位 2.546 秒，最大 4.076 秒 |
| 最终修复计算 | 3.243 秒 |
| 最终结果就绪 | 首个音频包后 34.974 秒 |
| 距预计播放结束 | 提前 11.370 秒 |
| 已发布乱序结果 | 0 次 |
| 冲突窗口 | 2 次，拒绝发布并安排修复 |
| 边界修订 | 536 个单元边界修订记录，最大移动 970 毫秒 |

11 项针对性测试通过。已验证取消后的结果抑制与后台进程退出。

## C 首次结果的可用性

176 / 197 个单元首次发布早于预计播放起点。最差首次结果晚了 2.144 秒，因此当前不能承诺所有时间戳提前 t 毫秒准备好，连 t=0 也不能保证。

13 个关键词中，11 个首次发布早于预计播放起点。首次关键词边界与本次最终修复结果相比，P95 差异为 548 毫秒，最大 590 毫秒。这是算法版本间比较，不是人工标注准确率。

当前不增加播放缓冲。所有时间均相对于回复音频文件起点，不是设备实际发声回执。回放未同时运行 AEC，现场耗时可能更高。

首次发布的关键词试听：[13 个切片](/home/fk/.local/state/guidebot/conversation/phrase-alignment/f1b32726-cda0-453a-8c76-ed204c6acb0f/live-replay-validated/listen.md)。切片没有额外补边，包含由最终修复才补齐的关键词。

## D 真实场景验收

在 GuideBot Conda 环境运行：

```bash
python /home/fk/GuideBot-UniTree/GuideBot/conversation/conversation.py --timestamps
```

保留 LocalVQE AEC、0 毫秒参考延迟、4999 VAD 门槛、播放期间 −35 dBFS 门限及录音诊断默认值。

按 Enter 开始，请机器人给出一段较长介绍，先让它完整播放；再发起另一轮并尝试打断，最后按 Enter 结束。

新会话目录中的 `alignment.jsonl` 保存所有字级时间戳、版本、计算耗时与修订；`alignment-worker.log` 保存模型日志。终端会提示临时更新、前缀重同步和最终修复。

请提供会话目录。下一步将核对真实 AEC 负载下的计算耗时、首次发布时间、修订幅度与打断后的结果清理，再决定是否作为默认功能。
