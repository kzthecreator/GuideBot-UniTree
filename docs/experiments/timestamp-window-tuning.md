# 流式时间戳窗口参数回放对比

记录日期：2026-11-17，Asia/Shanghai。

使用已归档的 45.48 秒、197 个单元长回复，按录音中音频包的原始到达节奏，通过生产 `StreamingTimestamps` 子进程回放。未连接机器人、麦克风或云端。模型主要依据文本长度估计边界，因此这些数字只比较算法版本，不代表人工标注准确率。

| 设置 | 默认基线 | 较短窗口实验 |
|---|---:|---:|
| 窗口 / 更新间隔 / 尾留 / 前缀重同步 | 6 / 2 / 1 / 10 秒 | 3 / 0.75 / 0.35 / 8 秒 |
| 临时更新数 | 21 | 30 |
| 近期窗口计算中位数 / 最大值 | 0.772 / 0.832 秒 | 0.467 / 0.542 秒 |
| 前缀重同步数 | 4 | 7 |
| 首次发布早于预计播放起点 | 175 / 197 | 187 / 197 |
| 最差首次发布时间余量 | -2.233 秒 | -0.689 秒 |
| 关键词首次边界相对最终修复 P95 / 最大差异 | 460 / 460 ms | 298 / 370 ms |
| 所有单元边界修订记录 / 最大单次移动 | 644 / 970 ms | 560 / 700 ms |
| 完整结果就绪 / 最终计算耗时 | 36.497 / 3.357 秒 | 37.955 / 3.304 秒 |
| 距估计播放结束 | 提前 9.848 秒 | 提前 8.390 秒 |
| 顺序冲突 / 游标丢失警告 | 0 / 0 | 4 / 4 |

较短配置改善了近期窗口计算耗时、首次覆盖率和首发边界修订，但仍有 10 个单元首次发布时间晚于预计播放起点。较短历史窗口更容易产生顺序冲突；尾留更短时，最后一段出现游标丢失，只能等待完整修复。完整结果反而比基线晚 1.458 秒就绪。两组的计算耗时受 CPU 调度影响，单次回放不足以证明稳定收益。

结论：不调整在线默认参数，也不进入现场验证。下一步先保留较短窗口带来的计算收益，同时单独调大尾留或改进冲突后的恢复策略，再重复离线回放；选出无游标丢失、首次延迟可接受的设置后，才讨论手动现场验证。播放起点仍是 SDK 提交后的估计值，不是设备 DAC 发声回执；该回放不能证明硬件提前量。

实验输出位于本机 `recordings/long-reply/replay-baseline/` 与 `recordings/long-reply/replay-short/`，其中包括逐版本事件、计算耗时、修订和审阅结果。
