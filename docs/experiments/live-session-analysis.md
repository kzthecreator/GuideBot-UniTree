## D 原因与建议

最初需要积累约 2 秒音频，再花约 0.45–0.61 秒计算首批结果，并保留约 1 秒尾部。扬声器约在收到首秒音频后就开始播放，因此首批时间戳通常已经落后。

长回复后半段，云端生成逐渐领先于实际播放，时间戳才获得余量。第三轮完整结果在第 68.677 秒就绪，预计第 72.230 秒播完。这不代表前面每个字都提前就绪。

此次已验证后台运行、完整覆盖和打断清理。没有验证人工边界准确率，也没有证明严格的提前量保证。

建议下一步先缩短首批窗口、更新间隔及尾部保留，使用本次保存的数据回放比较。主要看首次发布时间、边界误差和 CPU 耗时是否改善。暂不修改当前默认参数。

如果业务最终要求所有关键词在发声前就有时间戳，需要在提前量不足时等待对齐结果，或者增加播放缓冲。仅靠当前异步旁路计算无法保证 t≥0。本次约 2.5 秒额外缓冲只能覆盖本次观测，不能当成所有场景的保证值。
